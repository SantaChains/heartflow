# 会话持久化与压缩归档设计

> 状态：设计定稿，未实施。本文只描述改造方案，不改动代码。
> 触发案例：`~/.heartflow/sessions/1795784782269-17808.json` 压缩后只剩 8 条消息，无 `.jsonl` 附段，压缩前的工具调用不可回溯。

## 1. 结论

当前实现把"会话"当作**可变状态**持久化：每回合用一份完整 JSON 覆盖上一份，压缩时在内存里 `mem::take` 掉旧消息、只留摘要。这不是日志模型，任何一次原地改写（压缩、/pin、任务上下文重置）都会让之前的状态永久消失。因此"谁在什么时候调了什么工具"这类问题在盘上无解，不是模型推理问题。

修复方向不是加一个更大的记忆，而是把持久化拆成**三层**：

| 层 | 角色 | 生命周期 | 当前状态 |
| --- | --- | --- | --- |
| 快照 `<id>.json` | 恢复缓存，可重建 | 每回合覆写 | 已有 |
| 活跃段 `<id>.jsonl` | 上次快照之后的增量日志 | 每回合截断复位 | 只有读端 |
| 归档 `archive/<id>/` | 压缩丢弃区的不可变副本 + 清单 | 只增不改 | 缺失 |

补齐后，`快照 + 全部归档` 可以按压缩世代拼回完整会话；活跃段负责回合内崩溃恢复；两者都带时间戳，工具调用可与文件 mtime 对齐。

## 2. 现状与证据

### 2.1 数据流

```
run_turn ──push──▶ session.messages ──save_session──▶ <id>.json（原子覆写）
                          │                    └──▶ SQLite 镜像（缩表时 DELETE + 全量重写）
                          │
                          └──compact（mem::take）──▶ 摘要 system 消息
                                   └──▶ 其余消息被丢弃，无落盘
```

### 2.2 代码实证

- 快照每回合覆写：[storage.rs](../crates/cli/src/storage.rs#L152-L174)。`path = dir.join(format!("{}.json", id))`，`save_to_path` 走 temp+rename，只保留最后一份。
- 压缩是破坏性的：[compact.rs](../crates/runtime/src/compact.rs#L732-L820)。`std::mem::take(&mut session.messages)` 之后，`to_summarize` 只用于生成摘要，函数返回时被丢弃；`CompactionResult` 只有 `summary` 和 `removed_message_count`。
- 唯一持久痕迹是计数：[compact.rs](../crates/runtime/src/compact.rs#L145-L179) 把 `count/removed_total` 写进 `compaction-stats.json`，没有内容、没有会话 id、没有时间。
- 追加段只有读端：[session.rs](../crates/runtime/src/session.rs#L191-L239) 有 `load_with_segment`、[parse_segment](../crates/runtime/src/session.rs#L310-L366)、`SEGMENT_VERSION`、撕裂尾容忍、base 校验；全仓库没有任何 `.jsonl` 写入点。
- 测试手工造段掩盖缺口：[e2e.rs](../crates/cli/tests/e2e.rs#L106-L135) 用 `fs::write` 造 jsonl，并在末尾手工 `remove_file`。真实运行不会产生段，段被合并进快照后也无人清理。
- 镜像继承同一缺陷：[storage.rs](../crates/cli/src/storage.rs#L296-L379) 镜像的是压缩后的内存 transcript；缩表时 [store.save_session](../crates/store/src/lib.rs#L169-L191) 先 `DELETE FROM messages` 再全量写，历史同样被截断。
- 消息没有时间戳：[session.rs](../crates/runtime/src/session.rs#L49-L60) 只有 `role/blocks/usage/pinned`，所以即使消息还在，也不能和 21:11 / 21:22 的文件 mtime 对齐。
- 摘要递归：[compact.rs](../crates/runtime/src/compact.rs#L870-L895) 不跳过 system 续接头，当前快照第一条摘要里已经出现 `- system: This session is being continued from a previous conversation...`，即上一轮的续接模板被当正文再摘要。
- 文档失真：[roadmap.md](../docs/src/roadmap.md#L626-L668) 第 18 条现状盘点写的是"会话：JSONL 落盘"，计划中的 B1/B2 也据此假设全历史可检索。实现与设计不一致。

### 2.3 运行数据

本机 `~/.heartflow/sessions/`：

- `compaction-stats.json`：`count=2882`，`removed_total=9693`，`window_half=0`，`absolute=2882`。约每 3.4 条消息就压缩一次，全部走绝对阈值，属于主路径而非边角。
- 目录下 10 个会话文件全是 `.json`，无 `.jsonl`。
- 目标快照 8 条消息，首条是压缩摘要，摘要内部又包含上一次的续接模板。

### 2.4 影响

1. 事故复盘不可做：压缩前的工具名、参数、结果、时间全部不可恢复。
2. roadmap B1 的"全历史搜索"失效：SQLite 里也没有被压缩掉的行。
3. 文档把未实现能力当既有事实，会继续误导后续设计。
4. 回合内崩溃会丢失已完成工具调用的记录，而工具已经改过真实文件。

## 3. 外部对标

### 3.1 Codex CLI（Rust，优先参考）

- 会话是追加式 JSONL rollout，每行 `RolloutLine { timestamp, ordinal, item }`；写入走后台 writer + 缓冲，`flush/persist` 显式落盘，并有 writer lock 与冷文件 `.zst` 压缩。
- 压缩不删日志，而是追加一条 `CompactedItem { message, replacement_history, ... }`；恢复时从最近一次压缩检查点开始重放，原始记录仍在盘上。
- 持久化前有 policy 层决定哪些条目入库，工具输出超过 64 KiB 会被截断并标注。
- 参考路径：`codex-rs/rollout/src/recorder.rs`、`codex-rs/rollout/src/policy.rs`、`codex-rs/history/src/lib.rs`（`CompactedItem`）、`codex-rs/core/src/compact.rs`。

结论：采用"日志 + 检查点"的思想，但不照搬整仓结构；我们的 JSON 快照继续作为恢复缓存，避免一次性迁移到唯一日志源的回归风险。

### 3.2 Claude Code

官方文档明确：每个会话保存为一个 `.jsonl` transcript 文件，工作过程中持续写入；压缩后会话里会出现一行 `Conversation compacted`，恢复时从最后一次压缩的摘要和其后的条目继续，压缩前的行仍在文件里。
来源：<https://code.claude.com/docs/en/sessions>

### 3.3 Gemini CLI

checkpoint 同时保存完整对话历史、文件快照和待执行的工具调用，`/restore` 会回滚文件并恢复对话历史。它证明"压缩/检查点必须包含可恢复的历史，而不只是摘要"。
来源：<https://geminicli.com/docs/cli/checkpointing/>

### 3.4 Goose（Rust）

会话存 SQLite（`sessions.db`），消息逐条持久化，压缩表现为替换会话内容。它说明 SQLite 可行，但仅靠"替换"同样会丢历史，除非另留归档表。
来源：<https://deepwiki.com/aaif-goose/goose/2.4-session-and-storage>

### 3.5 取舍

| 方案 | 采纳 | 理由 |
| --- | --- | --- |
| 追加式日志作为唯一真源 | 否 | 迁移面大，启动恢复慢，现有 `/open`、快照格式、cassette 测试都要改 |
| 日志 + 检查点，快照保留为缓存 | 是 | 与 Codex 同构，改动可分阶段，现有恢复路径不被破坏 |
| 压缩前归档丢弃区 | 是 | 直接修复本次事故，成本最低 |
| 用 SQLite 取代 JSON 快照 | 否 | 可读性、可手工修复、权限模型都更差；SQLite 仅做检索镜像 |
| 冷会话 zstd 压缩 | 延后 | 需要新依赖与迁移，等归档量有实测后再做 |

## 4. 目标模型

```
sessions/
  <id>.json                     快照：当前会话状态（恢复缓存，权威但可重建）
  <id>.jsonl                    活跃段：上次快照之后的新消息（回合内崩溃恢复）
  compaction-stats.json         聚合计数（保留，增加字段）
  archive/
    <id>/
      manifest.jsonl            归档清单：每次压缩一行
      0001.json                 第 1 次压缩丢弃区（不可变）
      0002.json
```

不变式：

- INV1 快照自洽：单独加载 `<id>.json` 永远得到可用会话。
- INV2 段只做增量：`<id>.jsonl` 的 header `base` 必须等于快照消息数，否则整段拒绝（沿用现有语义）。
- INV3 归档只增不改：压缩丢弃区一旦写入 `archive/`，任何路径都不删除、不改写。
- INV4 全量可重建：按 `epoch` 顺序拼接所有归档的 `messages`，再接当前快照的消息，可还原压缩前的完整消息序列（被摘要替换的部分由归档保留，摘要本身是新增的 system 消息）。
- INV5 敏感信息一致：快照、段、归档、SQLite 镜像走同一套 `redact_messages` 规则，任何一层都不落明文凭据。

## 5. 落地设计

### A. 压缩归档（P0，先修事故）

目标：每一次压缩丢弃的消息，在压缩发生的同一回合内落到 `archive/<id>/`，且失败不阻断回合。

#### A1 数据结构

`CompactionResult` 增加丢弃区与触发原因（[compact.rs](../crates/runtime/src/compact.rs#L490-L494)）：

```rust
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct CompactionResult {
    pub summary: String,
    pub removed_message_count: usize,
    /// 被折叠进摘要、即将从 transcript 消失的消息（pinned 幸存者不在内）。
    pub dropped: Vec<ConversationMessage>,
    /// 本次压缩的触发来源，写入归档元数据。
    pub trigger: ThresholdKind,
}
```

`dropped` 直接移入返回值，不 clone：`compact_session_in_place_with` 里 `to_summarize` 在生成摘要后本来就是死值，`mem::take` 的所有权链路可以一路传到归档写入点。

归档文件格式（单文件、带元数据头；写入复用 `save_to_path` 的 temp+rename/重试/权限加固逻辑，抽成通用 `write_atomic(path, bytes)`）：

```json
{
  "version": 1,
  "ts": 1795786000123,
  "session": "1795784782269-17808",
  "epoch": 3,
  "reason": "absolute",
  "removed": 35,
  "messages": [ ... ]
}
```

清单行（`manifest.jsonl`，每次压缩追加一行，O_APPEND）：

```json
{"version":1,"ts":1795786000123,"epoch":3,"file":"0003.json","removed":35,"bytes":148213,"reason":"absolute"}
```

`epoch` 取 `manifest.jsonl` 现有行数 + 1；文件名 `{:04}.json`。`ts` 统一为毫秒 `u64`（`storage::unix_millis` 返回 `u128`，用 `u64::try_from(..).unwrap_or(u64::MAX)` 截断）。

#### A2 运行时接线

`ConversationRuntime`（[conversation.rs](../crates/runtime/src/conversation.rs#L1816-L1826)）增加待归档缓冲。一个回合内可能压缩多次（D4.2 硬触发的一级/二级降级），所以缓冲按"每次压缩一项"保存，不能拍平成一个大 Vec，否则归档会丢失压缩世代边界：

```rust
struct CompactionAudit {
    reason: String,                     // auto / hard_retry / manual / task_reset
    messages: Vec<ConversationMessage>,
}

pending_archive: Vec<CompactionAudit>,

fn compact_with(...) -> CompactionResult {
    let mut result = compact_session_in_place_with(...);
    if !result.dropped.is_empty() {
        self.pending_archive.push(CompactionAudit {
            reason: reason_for(result.trigger),
            messages: std::mem::take(&mut result.dropped),  // 移动，不拷贝
        });
    }
    self.token_prefix.set((0, 0));
    result
}

/// 回合边界取走待归档区；无压缩时返回空。
pub fn take_compaction_audit(&mut self) -> Vec<CompactionAudit>;
```

`mem::take` 把丢弃区整体移入缓冲，没有 clone；调用方从缓冲取走后逐项写入归档。内存峰值只是"被丢弃区恰好活到回合结束"，与压缩前本来就在内存里的量相同。

`reset_for_task`（[conversation.rs](../crates/runtime/src/conversation.rs#L2020-L2023)）同样把被替换的旧消息作为 `reason: "task_reset"` 推入 `pending_archive`，任务上下文切换不应成为审计缺口。

#### A3 落盘接口

在 [storage.rs](../crates/cli/src/storage.rs) 新增，复用现有原子写与目录加固：

```rust
pub(crate) fn archive_dir() -> PathBuf {
    sessions_dir().join("archive")
}

/// 写入一次压缩的丢弃区；返回归档文件路径。
/// 失败只记录并计数，绝不向上传播为回合失败。
pub(crate) fn archive_compaction(
    state: &SessionShared,
    audit: CompactionAudit,
) -> io::Result<Option<PathBuf>> {
    if audit.messages.is_empty() { return Ok(None); }
    let messages = redact_messages(&audit.messages, &registered_secrets(state));
    let dir = archive_dir().join(current_session_id(state));
    fs::create_dir_all(&dir)?;
    runtime::harden_dir(&dir);
    let epoch = next_epoch(&dir)?;              // manifest 行数 + 1，目录内串行
    let record = CompactionArchive {
        version: 1,
        ts: unix_millis_u64(),
        session: current_session_id(state),
        epoch,
        reason: audit.reason,
        removed: messages.len(),
        messages,
    };
    let path = dir.join(format!("{epoch:04}.json"));
    // 复用 save_to_path 的 temp+rename/重试/权限加固，抽出通用 write_atomic(path, bytes)；
    // 归档记录带元数据，不能直接复用只序列化 {version,messages} 的 Session::save_to_path。
    write_atomic(&path, &serde_json::to_vec_pretty(&record)?)?;
    append_manifest(&dir, &record, &path)?;     // 单行 write_all + flush
    Ok(Some(path))
}
```

丢弃区在写入前必须过一遍 `redact_messages(&audit.messages, &registered_secrets(state))`，与快照同规则（security.dev.md D9）；代码里已内联这一步，不要依赖调用方先脱敏。

#### A4 调用点

| 场景 | 位置 | 处理 |
| --- | --- | --- |
| 回合内自动压缩 | [conversation.rs:1105](../crates/runtime/src/conversation.rs#L1105-L1120) | 缓冲，回合结束时统一落盘（一项一文件） |
| 回合结束 | [turn.rs:594](../crates/cli/src/turn.rs#L594-L602)（REPL）、[stream.rs:436](../crates/cli/src/tui/stream.rs#L436-L438)（TUI） | 先逐项 `archive_compaction()`，再 `save_session_async` |
| 回合后补偿压缩 | [main.rs:1794](../crates/cli/src/main.rs#L1794-L1807) `maybe_auto_compact` | `runtime.compact` 后立即归档 |
| 手动 `/compact` | [slash.rs:358](../crates/cli/src/slash.rs#L354-L369) `force_compact` | 同上 |
| `--run /compact` | [commands/lib.rs:51](../crates/commands/src/lib.rs#L50-L63) | `SlashCommandResult` 增加 `audit`，由 [main.rs:762](../crates/cli/src/main.rs#L762-L765) 写盘 |

顺序要求：归档先于快照保存。压缩后丢弃区只剩下内存里这一份，快照一旦成功写盘，内存中的会话就是压缩后的版本；如果先存快照再归档而归档失败，丢弃区将永久消失。反过来先归档、后存快照失败，损失只是"本回合的压缩结果没落盘"，归档内容仍然有效，不会重复也不会丢数据。回合内压缩的归档在回合结束落盘，距压缩只有一次工具往返的时间窗；这个窗口内的崩溃由 B 阶段的活跃段兜底。

失败语义：`archive_compaction` 返回 `Err` 时打印一行警告并 `tracing::warn!`，回合继续；同一进程只警告一次，避免磁盘异常时刷屏。失败计数不需要写进 runtime 的 stats 文件（跨 crate 写入会把 CLI 关注点塞回 runtime），由 `hf doctor` 扫描 `archive/` 的"有文件无清单行 / 有清单行无文件"来发现不一致。

#### A5 收尾

- `hf doctor` 新增一行：归档会话数、文件数、总字节、最近归档时间、孤立文件数。数据来自目录扫描（归档是低频写入，扫描成本可忽略）。
- 不新增 stats 字段；`compaction-stats.json` 的格式保持不变，避免 runtime 与 CLI 互相改写同一文件。

### B. 活跃段写端（P1，回合内崩溃恢复 + 精确时间）

目标：给现有 `load_with_segment` 补上生产者，并让段记录带时间戳。

#### B1 格式版本

`SEGMENT_VERSION` 从 1 升到 2。v2 每行是信封：

```json
{"ts":1795786000123,"message":{"role":"assistant","blocks":[...]}}
```

header 不变：`{"base": <快照消息数>, "version": 2}`。`ts` 是毫秒 `u64`，由 runtime 侧新增的 `unix_ms()` 提供（`storage::unix_millis` 返回 `u128`，只在 CLI 边界使用）。

读端 `parse_segment` 同时支持两个版本：v1 行按 `ConversationMessage` 解析（兼容手写与测试），v2 行按信封解析；版本不在 `{1,2}` 内整段拒绝，沿用现有语义。

#### B2 写端

在 [session.rs](../crates/runtime/src/session.rs) 增加：

```rust
pub struct SegmentWriter {
    file: fs::File,
    path: PathBuf,
    base: usize,
    appended: usize,
}

impl SegmentWriter {
    /// 打开或创建段：
    /// - 不存在：写 header {base, version:2}；
    /// - 存在且 base 匹配：从尾部续写，先修复撕裂尾（见下）；
    /// - 存在但 base 不匹配：以当前 base 重建（快照已前进，旧段作废）。
    pub fn open(path: &Path, base: usize) -> io::Result<Self>;

    pub fn append(&mut self, ts: u64, message: &ConversationMessage) -> io::Result<()>;
    pub fn sync(&mut self) -> io::Result<()>;
}

/// 快照保存成功后复位段头：原子写 {"base": base, "version": 2}。
pub fn reset_segment(path: &Path, base: usize) -> io::Result<()>;
```

两个关键细节：

1. **撕裂尾修复**。`parse_segment` 把中间无法解析的行视为整段作废，因此写端在续写前必须把最后一条不完整记录截掉：从文件末尾按 64 KiB 块向前找最后一个 `\n`，`set_len` 到该位置之后。只在首次打开时做一次，摊到每回合可忽略。
2. **复位顺序**。先快照 rename 成功，再 `reset_segment`。两步之间崩溃时，旧段 `base` 小于新快照长度，读端按 INV2 拒绝并打印警告，不重复、不串位；最多丢一条 stderr 警告。

#### B3 运行时日志口

在 `ConversationRuntime` 增加可注入的 sink，避免 runtime 直接依赖磁盘与 home 目录：

```rust
pub trait SessionJournal: Send + Sync {
    /// 非阻塞：实现方自行排队；绝不能在这里阻塞回合。
    fn record(&self, ts_ms: u64, message: &ConversationMessage);
    /// 回合边界调用：排空队列并 sync 到盘。
    fn flush(&self) -> io::Result<()>;
}

impl ConversationRuntime {
    pub fn with_journal(mut self, journal: Arc<dyn SessionJournal>) -> Self;
}
```

[conversation.rs](../crates/runtime/src/conversation.rs) 里的 `self.session.messages.push(...)` 共 7 处（1226/1248/1300/1352/1577/1618/1781 行）改走一个私有方法：

```rust
fn push_message(&mut self, message: ConversationMessage) {
    if let Some(journal) = &self.journal {
        journal.record(unix_ms(), &message);
    }
    self.session.messages.push(message);
}
```

第 8 处（1751 行）在 `&mut Session` 的静态辅助函数里，拿不到 `self`：给该函数补一个 `journal: Option<&Arc<dyn SessionJournal>>` 参数，或在其调用点统一补记，二选一，以不复制函数体为准。

顺序是先记日志再入内存：若入内存后立即 panic，日志里已有该条，恢复时最多多一条孤立消息，`repair_tool_pairing` 会在请求构建时安全丢弃；反过来则丢记录。

#### B4 CLI 实现

`DiskJournal`（放在 [storage.rs](../crates/cli/src/storage.rs)）：

- 持有一个无界 `mpsc::Sender<JournalCmd>`，`record` 只做 `send`（不阻塞、不丢）；写线程负责脱敏、追加、按批 `flush`。
- 写线程持 `SessionShared` 的 clone，用于每次取 `registered_secrets` 并调用 `redact_messages`，与快照保持一致。
- `flush()` 发送 `Flush(ack)` 并阻塞等待，由调用方放进 `spawn_blocking`；只有收到 ack 才返回。
- 段路径与快照同目录：`sessions_dir().join(format!("{id}.jsonl"))`。

回合边界顺序：

```
1. journal.flush()                 // 排空 + sync
2. save_session_async()            // 快照原子覆写
3. reset_segment(path, len)        // 段头复位，下一回合从新 base 追加
4. archive 已在 A 阶段先完成
```

TUI 的 `TurnSaver` 增加 `flush_journal` 步骤；REPL 在 [turn.rs:560](../crates/cli/src/turn.rs#L556-L565) 与 [turn.rs:597](../crates/cli/src/turn.rs#L594-L602) 前后接入。

#### B5 崩溃矩阵

| 崩溃时点 | 盘上状态 | 恢复结果 |
| --- | --- | --- |
| 回合中，工具已执行 | 快照旧 + 段含新消息 | 段被应用，工具记录完整 |
| 段写一半 | 段尾撕裂 | 读端丢弃最后一条不完整记录，保留完整记录 |
| 快照 rename 后、段复位前 | 快照新 + 段 base 旧 | 段整体拒绝并警告；消息已在快照里 |
| 段复位后、下一回合前 | 快照新 + 段空 | 正常 |

### C. 检索层补全（P2）

目标：让 roadmap B1 的"全历史搜索"真的覆盖压缩前内容。

[store/src/lib.rs](../crates/store/src/lib.rs#L586-L643) schema 升到 v4：

```sql
CREATE TABLE IF NOT EXISTS archived_messages (
    id INTEGER PRIMARY KEY,
    session_id TEXT NOT NULL,
    epoch INTEGER NOT NULL,
    seq INTEGER NOT NULL,
    role TEXT NOT NULL,
    blocks_json TEXT NOT NULL,
    search_text TEXT NOT NULL,
    ts INTEGER,
    UNIQUE(session_id, epoch, seq)
);
CREATE VIRTUAL TABLE IF NOT EXISTS archived_fts USING fts5(
    search_text,
    tokenize='trigram'
);
```

- 写入：`Store::archive_messages(session_id, epoch, messages)`，只在 A3 归档成功后调用；`save_session` 的 `DELETE` 不触碰该表。
- 检索：`Store::search` 对 `messages_fts` 与 `archived_fts` 做 `UNION`，命中行带 `archived: true` 与 `epoch`，工具面可按需折叠。
- 迁移：`SCHEMA_VERSION = 4`；v3→v4 只建新表，不回填旧数据，旧会话在下次压缩前仍只有现有镜像。
- 顺带修正 roadmap 第 18 条的"JSONL 落盘"表述，改为"快照 + 活跃段 + 压缩归档"。

### D. 摘要去噪与压缩边界（P2）

1. `summarize_messages` 跳过续接 system 消息：`role == System` 且文本以 `This session is being continued from a previous conversation` 开头时整条跳过。避免模板被反复摘要，逐轮稀释真实信息。
2. 续接头里增加归档指针（当本次有归档时）：
   `A verbatim copy of the dropped region is archived at epoch N; older tool calls remain inspectable if needed.`
   模型知道可回溯，而不是只有一段会退化的摘要。
3. 单条摘要预算已有 `SUMMARY_MIN_CHARS/MAX_CHARS` 斜坡，保持不变；新增测试断言二次压缩后的摘要不含续接模板。

### E. 运维与可观测（P3）

- `hf doctor`：归档数量/字节/最近时间/失败计数；段 base 是否与快照一致；孤立归档（有文件无清单行）计数。
- 保留策略：默认不删除归档；当单会话归档超过 `archive_max_bytes`（默认 64 MiB）时，`hf doctor` 告警，不自动清理。后续可评估冷归档 zstd（Codex 做法），P0/P1 不引入新依赖。
- 写放大观测：每回合快照全量重写仍是 O(n)。本设计不改变这一点，只把 `save_session` 的实际字节数写进 tracing，作为后续是否改为"段为主、快照按需检查点"的数据依据。

## 6. 兼容与迁移

- 旧快照：无 `ts`、无段、无归档，`load_from_path` 行为不变；`from_json` 对未知字段宽容，新增字段不会被旧文件拒绝。
- 旧段：v1 明文行继续可读；由于历史上没有写端，实际只存在于测试与手写场景。
- 旧数据库：v3 库启动时建 `archived_*` 两表，`PRAGMA user_version` 升到 4，不改旧表。
- 首次升级后的第一个回合：快照写入成功后 `reset_segment` 生成 `{base, version:2}` 空段；不产生任何历史回填。
- 回退：A/B/C/D 各自独立提交。回退 B 只需不注入 journal（`with_journal` 不调用），读端仍能处理旧段；回退 A 不会破坏快照；回退 C 只需保留新表但不查询。
- 并发：会话 id 含 pid，正常不会有两个进程写同一目录；`--resume` 后新进程沿用旧 id，若旧进程仍活着则与现有快照语义一致（last-writer-wins）。归档 `epoch` 以 manifest 行数为准，不做跨进程锁；同一会话并发压缩属于既有不支持场景，本文不扩大承诺。

## 7. 测试计划

单元：

- `session.rs`：v1/v2 段解析；撕裂尾修复后追加不产生中间坏行；`reset_segment` 原子性；base 不匹配拒绝。
- `compact.rs`：`dropped` 内容 == `removed_message_count` 对应的消息；pinned 不入 `dropped`；`<= preserve_recent` 的保护路径 `dropped` 为空；二次压缩摘要不含续接模板。
- `conversation.rs`：用 `RecordingJournal` 断言每次 push 恰好 record 一次、顺序一致；`take_compaction_audit` 取走后清空；`reset_for_task` 把旧消息交给审计。
- `storage.rs`：归档文件内容脱敏；manifest 追加一行；epoch 递增；归档失败返回错误但不 panic。
- `store`：v4 迁移；`save_session` 全量重写后 `archived_messages` 仍在；搜索能命中归档行。

集成 / e2e：

- 故障注入：在工具结果 push 后、快照保存前 `abort`，重启 `--resume`，断言工具结果仍在且时间戳可读。
- 压缩后归档：一次会触发压缩的会话结束后，`archive/<id>/0001.json` 存在，且其中能找到压缩前调用的工具名与 id。
- 陈旧段：手工造 `base` 不匹配的段，`--resume` 成功且 stderr 只有一条警告；旧实现会打印同样警告但无数据损失，新增 e2e 固化该行为。
- 脱敏回归：注册一个假凭据，确认快照/段/归档/SQLite 四处都不含明文。

## 8. 验收标准

1. 复现原事故：一次真实会话压缩后，能在 `archive/<id>/` 找到 21:11 那次调用的工具名、参数、结果与时间戳，无需读摘要。
2. `sessions/<id>.jsonl` 在真实运行中存在，且 `base` 始终等于快照消息数；回合中 kill 进程后 `--resume` 能恢复该回合已完成的工具调用。
3. `hf search` 能命中被压缩掉的内容（`archived_messages` 生效）。
4. 再次压缩已压缩会话，摘要中不再出现 `This session is being continued...`。
5. `cargo test --workspace` 通过，`cargo clippy --workspace --all-targets -- -D warnings` 零告警；`hf doctor` 新增指标有值。

## 9. 明确不做

- 不把 SQLite 或 JSONL 变成唯一真源，快照继续作为恢复缓存。
- 不做向量记忆、跨设备同步、归档自动删除。
- 不改变每回合全量快照的写放大（只量化、不优化），留待数据支撑后再评估"段为主"。
- 不把 mission/job registry 内部结构暴露到工具面。
- 不在 P0/P1 引入 zstd 等新依赖。
