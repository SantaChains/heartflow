## KI-001 · Alt+Enter 在 pwsh 下触发全屏、无法进行多行续行

- **现象**：在交互式命令（实际执行 PowerShell，见 `error.md` 记录：`bash` 工具在 Windows 上跑的是 PowerShell）中输入多行命令时，按 **Alt+Enter** 不会像在普通终端里那样把光标移到下一行继续输入（续行），而是触发**全屏**表现（程序进入/切换全屏），换行意图落空。
- **环境·复现**：Windows + heartflow TUI（crossterm 原始模式 + 备用屏幕 `EnterAlternateScreen`，`crates/cli/src/tui.rs:60`、`:1679`）。在 TUI 内启动交互式/长运行命令（如 `bash` 工具跑 PowerShell）后，于输入态按 Alt+Enter。
- **影响**：无法在 TUI 内的 PowerShell 里输入多行脚本/续行；Alt+Enter 被「吃掉」或上抛到全屏语义，破坏正常编辑流。
- **疑点·待查位置（假设，未核实）**：
  - TUI 在原始模式 + 备用屏幕下运行（`tui.rs:1679` `enter()`），按键先经事件循环；`tui.rs:451` 注释明确「the loop intercepts these keys before the reducer sees them」——存在一层先于 reducer 的按键拦截。`tui.rs:527` 也把「modified arrow (ctrl/alt/super)」判为编辑器动作而非历史导航，说明修饰键组合在 TUI 层被特判。Alt+Enter 极可能在此层被消费，未转发到 PTY，pwsh 收不到续行信号。
  - 另一可能：宿主终端（Windows Terminal / ConPTY）在到达 PTY 前就把 Alt+Enter 解释为全屏切换，与 heartflow 的 raw/alt-screen 状态叠加。需真机区分是 TUI 层拦截还是宿主层语义。
  - 修复方向（待验证）：当交互式终端/输入态激活时，把 Alt+Enter 透传给 PTY 而非拦截/上抛；并确认不会与宿主全屏语义冲突。
- **登记日期**：2026-10-22
- **状态**：登记未修复

## KI-002 · Ctrl+C 提示文字显示时间过短，看不清消息

- **现象**：运行中按 **Ctrl+C** 触发打断时，界面给出的提示文字（如「再按一次确认打断」之类）**一闪而过**，来不及看清内容就消失。
- **环境·复现**：heartflow TUI 运行中（agent 回合或交互态），按 Ctrl+C。
- **影响**：用户无法从提示文字确认当前处于「已 armed 待二次确认」还是「已打断」状态，体验含糊，容易误按或不知已触发。
- **疑点·待查位置（假设，未核实）**：
  - `crates/cli/src/tui.rs:226` 有 `ctrl_c_armed: bool` 字段，L348/L394/L399-404/L712 围绕其实现「首次 Ctrl+C 武装、二次确认」的两段式打断；相关提示文字大概率走 `status_note`（如 L364 的 `permission requested …` 同类瞬时状态栏）渲染。若 `status_note` 在下一帧被覆盖、或 armed 态未把提示持续挂起，就会短暂闪现后消失。
  - 修复方向（待验证）：把打断/确认提示作为**持久状态栏**保留到动作结算或显式超时，而不是瞬时覆盖；或把该提示额外写一行到 transcript，确保可读。
- **登记日期**：2026-10-22
- **状态**：登记未修复
